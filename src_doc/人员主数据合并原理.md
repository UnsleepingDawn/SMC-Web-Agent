# 人员主数据合并原理

人员主数据来自两个飞书数据源：**通讯录**（身份与联系方式）和**组会多维表**（实验室自己维护的标签）。两者都不完整，合并后才是一份可用的人员表。

## 1. 两个数据源各自有什么

| 字段 | 通讯录 | 组会表 |
| --- | --- | --- |
| 姓名 | ✅ | ✅ |
| 培养类型 | ✅ | ✅ |
| 年级 | ❌ | ✅ |
| 导师 | ❌ | ✅ |
| 在读情况 | ❌ | ✅ |
| 学号 | ❌ | ✅ |
| `open_id` / `union_id` / `user_id` | ✅ | 只有 `open_id` |
| 邮箱 / 手机 / 部门 | ✅ | ❌ |

关键点是：**组会表里存着成员的飞书 `open_id`**（字段 `_飞书账号`），这成了连接两侧的天然外键。

## 2. 连接键与取值优先级

以 `open_id` 为键做**全外连接**：只在一侧出现的人也要保留，避免「通讯录里刚入职、组会表还没登记」或「组会表里已登记、但通讯录权限没覆盖」的人丢失。

冲突时的取值规则：

- 姓名、培养类型两边都有 → **通讯录优先**（通讯录是权威身份信息），同时记一条 conflict。
- 年级、导师、在读情况、学号只有组会表有 → 取组会表。
- `union_id` / `user_id` / 邮箱 / 手机 / 部门只有通讯录有 → 取通讯录。

冲突不是错误，而是提示：通讯录里改名了、组会表还写着旧名字，这类漂移需要人工确认，所以 `merge_members` 返回 `conflicts` 列表而不是静默覆盖。

## 3. `需要考勤` 的判定

```
need_attendance = feishu_user_id 非空 且 feishu_user_id ∈ 考勤组成员
```

考勤组成员由 `FEISHU_ATTENDANCE_GROUP_NAME`（默认 `SMC考勤`）对应的考勤组拉取。这条规则决定了：

- 谁应该提交周报（周报统计的「应提交」集合）。
- 谁需要组会签到（考勤模块预留）。

若应用没有考勤权限，同步会跳过这一步并记 warning，此时 `need_attendance` 全为 `false`，周报统计也就没有应提交名单——这是有意的降级，而不是错误。

## 4. 同步如何落库

1. `jobs` 拉取通讯录部门树与成员，得到 `address_rows`。
2. `jobs` 分页拉取组会表，`seminar_member_rows` 把每条记录压成一行（跳过没有 `open_id` 的行）。
3. `merge_members` 合并，产出 `members` 列表。
4. `jobs` 把结果 POST 到 `/api/webhooks/jobs/{run_id}`。
5. `server` 在 advisory lock 下按 `feishu_account` upsert：已存在则更新，不存在则插入。

`is_active` 在同步时统一置 `true`，人员在页面上的「离册」状态由人工维护，同步不会把它改回去。

## 5. 为什么不用姓名做键

同名、改名、拼音写法不一致都会让姓名匹配出错，而且组会表里的姓名可能是昵称。`open_id` 在同一企业内唯一且稳定，是唯一可靠的连接键；姓名只作为展示与冲突检测用。
