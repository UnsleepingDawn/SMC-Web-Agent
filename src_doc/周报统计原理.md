# 周报统计原理

周报统计要回答一个问题：**这一周谁该交、谁交了、谁没交**。

## 1. 应提交集合从哪来

「该交」不是取全部学生，而是取**考勤组成员**。理由是：只有需要打卡到实验室的人才需要每周汇报；联合培养、外派、已毕业的人不应被计入应提交名单。

基数只有考勤表这一个来源，但有两条取法，按用途区分：

| 用途 | 集合定义 | 取数 |
| --- | --- | --- |
| 首页卡片、海报、周报统计页顶部的计数 | `SMC考勤` 考勤组成员表的姓名；组数据为空时回退到 `need_attendance` | `attendance_group_names` |
| 缺交次数、周报总结推送名单、老师推送里各学生的状态 | `{ member.name \| member.need_attendance = true 且 member.is_active = true }` | `expected_members` |

`need_attendance` 在人员同步时由「是否属于 `SMC考勤` 考勤组」判定（见 [人员主数据合并原理.md](人员主数据合并原理.md)），所以两者通常一致。差别在于同步只会把新进组的成员置为 `true`，**从不回退**：已经退出考勤组的人仍然留着 `need_attendance = true`。计数改读考勤组成员表，分母就与考勤表人数严格一致，不会被这批历史遗留撑大。

`FEISHU_ATTENDANCE_GROUP_NAME`（默认 `SMC考勤`）决定读哪个组。考勤权限缺失会让组数据为空，此时回退到 `need_attendance`，所以降级不会让应提交集合变空——这一点与 [人员主数据合并原理.md](人员主数据合并原理.md) 描述的降级行为一致。

## 2. 提交集合从哪来

周报表按 `_Week` 与 `WeekdayValid` 两个条件筛选出本周有效记录，每条记录取：

- `汇报人` → `member_name`（可能是多人，取姓名拼接）
- `文档链接` → `doc_link`
- `附件` → `attachments`（JSONB 存 `file_token` 与文件名）
- `record_id` → 便于回查原始行

同一个人重复填写时**只保留第一条**（`seen` 集合去重），避免重复计数。

## 3. 差集算法

```
submitted_names = { 周报表里出现的姓名 }
missing = [expected 中不在 submitted_names 的人]
```

注意两个细节：

- 匹配用的是**姓名**而不是 `open_id`。周报表的「汇报人」是人员字段，但历史数据里存在手工输入的名字，且部分记录没有 ID，所以按姓名匹配是兼容性最好的做法。代价是改名后可能匹配不上——改名时应同时更新周报表。
- 有人在应提交集合之外提交了周报（例如旁听的同学），仍会列进「已提交」。在首页与海报的「已提交 X / 总 Y」里，这类人**分子分母各加 1**：`Y = 考勤组人数 + 额外提交者数`。这就是原项目的「额外提交者」语义。

## 4. 文案渲染

`weekly_summary.json` 模板渲染出三段：

1. 周报提交情况（标题）
2. 周报链接（可点击）
3. 已提交名单 / 未提交名单

全齐时「未提交」一行渲染为「无」，而不是留空——空行会让人怀疑是渲染失败。

## 5. 推送给老师

「推送给老师」把本周周报链接与每位老师名下学生的周报链接，私聊发给各位老师。

### 老师名单从哪来

老师名单**不需要维护**，它就是通讯录里 `Tenure` 部门的五位老师：

```
老师 = { member | member.department == FEISHU_TEACHER_DEPARTMENT_NAME 且 is_active }
```

部门名默认 `Tenure`，可用环境变量 `FEISHU_TEACHER_DEPARTMENT_NAME` 覆盖。`department` 在同步人员时取自通讯录（见 [人员主数据合并原理.md](人员主数据合并原理.md)），所以人事变动只要重新同步人员，老师名单自动更新。

`open_id` 取 `member.feishu_account`；缺 `open_id` 的老师在页面上标记并禁用勾选。

管理员（先收一份核对的人），通常不用配置。取值优先级：

1. `runtime_configs` 的 `weekly_push_admin_open_id`（设置页可填）；
2. 环境变量 `SMC_ADMIN_OPEN_ID`（compose 里的默认值）；
3. 代码内置默认 `DEFAULT_WEEKLY_PUSH_ADMIN_OPEN_ID`。

所以只要其中任一层有值，`admin_configured` 就为真，「先发给管理员」按钮才可点。

### 学生怎么分组

```
在读学生 = { member | member.enrollment_status == "在读" }
老师的学生 = { 在读学生 | member.advisor == 老师姓名 }
```

按**导师姓名的精确匹配**分组（导师字段来自组会表）。姓名不一致的老师会分到 0 个学生，页面标为「无在读学生」并禁用勾选；这通常说明组会表的「导师」写法和通讯录姓名对不上。

每位学生的状态取自本周周报记录（与已提交/未提交统计同一份数据），判定顺序为：

1. 有文档链接 → 消息里可点击「查看周报」，页面标为「已提交（飞书链接）」，其中「飞书链接」四字本身是指向该周报的超链接；
2. 没有链接但有附件 → 「已提交（文件）」；
3. 没有记录 → 「未提交」。

周报统计页上每位老师姓名左侧有三角，可展开组内学生名单与各自状态；同理，推送给老师的消息也按同一顺序渲染学生状态。「已提交（文件）」对应周报表里填了「附件」但没有「文档链接」的记录。

学生行是 `姓名 | 状态` 两列网格，姓名占固定宽度（4 个中文字符），所以姓名长短不影响状态列对齐；超过宽度的姓名截断显示。

组内学生的排列顺序与状态判定一致：**已提交的排在前面**，已提交里**有文档链接的又排在仅附件的前面**，同一档内按姓名（沿用 `list_enrolled` 的 `Member.name` 排序）。这个顺序在 `_teacher_push_plan` 里排好后同时供页面和推送消息使用，所以两处顺序一致。

### 两段确认

1. 点「推送给老师」先弹窗，选项是「取消 / 先发给管理员 / 确认」。
2. 「先发给管理员」会把**与即将发给老师完全相同的内容**逐条私聊给管理员（`template_key=weekly_teacher_reports_preview`，标题带「（发给X老师）」），然后弹第二个「请确认无误」弹窗，选项是「取消 / 确认」。
3. 「确认」直接把消息发给老师本人（`template_key=weekly_teacher_reports`）。

每个收件人都先写 `notifications` 再投递 `jobs`，所以「先发给管理员」也是一条真实推送记录，可追踪。发送接口按老师名单顺序逐条投递，0 学生的老师跳过并在响应 `skipped` 里返回。

### 失败怎么提示

飞书消息由 `jobs` 异步发送，所以 POST 返回时只能确认「任务已投递」。接口为每个成功投递的老师返回 `notifications`（老师与 `notification_id` 的对应），同时把 `student_count == 0`、缺 `open_id`、创建推送记录失败、投递任务抛异常的老师分别记进 `skipped` 与 `failed`。

前端拿到响应后：

1. 立刻把 `failed` / `skipped` 组装成问题列表，红色提示框列出「老师：原因」，并弹红色 toast；
2. 若响应带 `notifications`，轮询 `GET /api/notifications/statuses?ids=...`（2 秒一次、最多 30 秒），`jobs` 通过 webhook 把结果写回 `notifications.status`（`sent` / `failed`）；
3. 轮询到的 `failed` 记录与超时未确认的 id 也并入问题列表。

因此「先发给管理员」失败时不会进入第二个确认弹窗，而是回到卡片并显示红框，避免在管理员没收到内容的情况下继续发给老师。

### 勾选与展开状态怎么保留

老师的勾选与三角展开状态按**用户 + 学期**存在 `weekly_push_drafts` 表（`teacher_names`、`expanded_teachers`），页面进入时恢复一次，之后改动防抖 500ms 回写，点「确认」推送成功时再回写一次。这与小组会议排班草稿是同一套机制。

恢复只认第一次：后续飞书同步触发的 `refetchPlan()`、切换周次都不会再把选择重置为「全部老师」。恢复时会与当前可选老师名求交集，名单里已消失的老师自动忽略；没有草稿时回退为「可选老师全选」。

## 6. 缺交次数怎么算

页面「缺交次数」卡片统计的是**自上次提交周报后的累计缺交周数**，口径与「第 N 周已提交/未提交」不同：后者只看所选那一周，前者会往前累计。

对每个「应提交」成员（取 `expected_members`，即 `need_attendance = true 且 is_active = true`，见第 1 节表格第二行），只看第 1 周到所选周次（含）：

- 区间内一条提交记录都没有 → `never_submitted = true`，缺交次数 = 所选周次（第 1 到第 N 周每周都算一次）。
- 区间内有提交 → 记最后一次提交的周次为 `last`，缺交次数 = `所选周次 - last`（即 `last+1 .. 所选周` 这些没有记录的周）。

所以还没同步的周会按缺交计：即使成员实际交过，只要数据没同步进来，也会显示缺交，同步完成后数字会回落。

图表只列缺交次数大于 0 的成员（缺交 0 表示本周已交，不占位），按缺交次数降序、同次数按姓名排序。颜色分两种：`never_submitted` 用红色 `bg-rose-500`（从未提交），提交过但之后缺交的用黄色 `bg-amber-500`。

接口是 `GET /api/weekly-reports/missed?week=N&semester_id=...`，返回 `{ week, chart: [{ name, missed, never_submitted }] }`。

## 7. 定时任务

`WEEKLY_SUMMARY_SCHEDULE`（默认周一 01:40 北京时间）触发 `send_scheduled_weekly_summary`，回打 `server` 的 `/api/webhooks/scheduled/weekly_summary`。`server` 计算「上周」（`previous_week`）并渲染推送，规则改动只改 `server`。
