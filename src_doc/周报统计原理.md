# 周报统计原理

周报统计要回答一个问题：**这一周谁该交、谁交了、谁没交**。

## 1. 应提交集合从哪来

「该交」不是取全部学生，而是取**考勤组成员**。理由是：只有需要打卡到实验室的人才需要每周汇报；联合培养、外派、已毕业的人不应被催交。

集合定义：

```
expected = { member.name | member.need_attendance = true 且 member.is_active = true }
```

`need_attendance` 在人员同步时由「是否属于 `SMC考勤` 考勤组」判定（见 [人员主数据合并原理.md](人员主数据合并原理.md)）。这也是为什么考勤权限缺失时周报统计会没有名单——应提交集合为空。

## 2. 提交集合从哪来

周报表按 `_Week` 与 `WeekdayValid` 两个条件筛选出本周有效记录，每条记录取：

- `汇报人` → `member_name`（可能是多人，取姓名拼接）
- `文档链接` → `doc_link`
- `附件` → `attachments`（JSONB 存 `file_token` 与文件名）
- `record_id` → 便于回查原始行

同一个人重复填写时**只保留第一条**（`seen` 集合去重），避免重复计数。

## 3. 差集算法

```
submitted_names = { 周报表里出现的姓名 }
missing = [expected 中不在 submitted_names 的人]
```

注意两个细节：

- 匹配用的是**姓名**而不是 `open_id`。周报表的「汇报人」是人员字段，但历史数据里存在手工输入的名字，且部分记录没有 ID，所以按姓名匹配是兼容性最好的做法。代价是改名后可能匹配不上——改名时应同时更新周报表。
- 有人在应提交集合之外提交了周报（例如旁听的同学），仍会列进「已提交」，但不会被计入应提交总数。这对应原项目的「额外提交者」语义。

## 4. 文案渲染

`weekly_summary.json` 模板渲染出三段：

1. 周报提交情况（标题）
2. 周报链接（可点击）
3. 已提交名单 / 未提交名单

全齐时「未提交」一行渲染为「无」，而不是留空——空行会让人怀疑是渲染失败。

## 5. 催交

催交对**每位未提交成员**单独发一条私聊消息：

- 目标取 `member.feishu_account`（`open_id`）；没有 `open_id` 的成员跳过并记 warning，不会让整个任务失败。
- 每条消息都先写 `notifications(template_key=weekly_reminder, status=pending)`，再由 `jobs` 发送并回写结果。
- 返回 `{sent: N}`，页面据此提示「已向 N 人发送催交消息」。

催交是幂等的「手动动作」，不做去重——重复点按钮就会重复提醒，这是操作者的意图。

## 6. 定时任务

`WEEKLY_SUMMARY_SCHEDULE`（默认周一 01:40 北京时间）触发 `send_scheduled_weekly_summary`，回打 `server` 的 `/api/webhooks/scheduled/weekly_summary`。`server` 计算「上周」（`previous_week`）并渲染推送，规则改动只改 `server`。
